# Agent Rules for FFX Monster AI & Stats Tool

1. **Always Require Implementation Plan Approval**: Before making ANY code changes or file creations/deletions, you must write an implementation plan (updating `implementation_plan.md` or creating a new plan) and wait for the user's explicit approval.
2. **Restricted Git Usage**: NEVER execute any git command (including `git status`, `git add`, `git commit`, `git diff`, or `git push`) unless the user explicitly instructs you to perform it.
3. **Unified Theme Adherence (No Ad-Hoc Styling)**: When creating or modifying Tkinter widgets, never hardcode background, foreground, or highlight colors. Always use the active theme references (e.g., `self.bg_color`, `self.accent_color`, `self.border_color`) and set helper tags like `_is_card = True` or `_is_title = True`, or register custom hover effects with `self.bind_hover()`, so the UI updates dynamically when a custom theme is selected.
4. **Mandatory Cleanup of Spawned Subprocesses**: Any background subprocess or thread spawned by code (like batch utilities, compilers, or listeners) must be properly terminated during window close/exit hooks to prevent "ghost" background processes from running after the tool is closed.
5. **Basic Emojis Only (Tcl/Tk Spacing Safeguard)**: Tkinter's underlying Tcl/Tk engine has layout issues with composite emoji sequences (like `🛠️` with variation selectors). Always use basic, single-unit emojis (e.g., `🔧`, `⏩`, `🧪`, `📖`, `🎲`, `⚖️`, `📊`, `📦`) in titles, manifests, and buttons to prevent Tcl from miscalculating character widths and inserting blank spacer layouts.
6. **Safe Path Manipulation**: Always use `os.path.join` and proper normalization (`os.path.abspath`) for directories. Ensure paths handle Windows case-insensitivity but remain compatible with Linux/Proton case-sensitivity for Steam Deck modding setups.
7. **Changelog Management Workflow**: Maintain a draft changelog file at `changelogs/RELEASE_vx.x.x.md` listing all changes made since the last official release. When the user signals that an official release has been published, rename `RELEASE_vx.x.x.md` to match the release version (e.g., `RELEASE_v1.1.0.md`) and create a new blank `RELEASE_vx.x.x.md` draft for subsequent changes.
8. **Mod Page Documentation Workflow**: When modifying `updated_mod_page.md` to reflect a new version, always merge the previous version's update highlights into the "🌟 Core Features" section, and create a new update highlights section (e.g., `[heading]⚡ New in vX.X.X[/heading]`) placed at the very top of the page (above Core Features) detailing the newest version's additions.
9. **Synchronized Application Versioning**: Whenever the application version is updated (e.g., bumping version in `FFX_AI_Tool.py`), you must synchronously update all related version definitions across the project, including the file properties compilation metadata in `ffx_ai_tool_version.txt`.
10. **GitHub README Synchronization Workflow**: Whenever the application version or `updated_mod_page.md` is updated for a release, `README.md` must be updated synchronously: its direct download link must point to the new release package URL, and its `## 🌟 Core Features` list must be fully synchronized with the master features list in `updated_mod_page.md` (converted from BBCode to GitHub Markdown).
11. **Google Doc Reference Link**: Whenever the user asks to "check the google doc", "look at the doc", or refers to the project analysis/roadmap document, fetch and reference the provided master documentation URL.
12. **Explicit Release Differentiation (Push vs. Release)**: A user command to "push", "git push", or "do a push" refers strictly to pushing current work-in-progress code changes to GitHub. NEVER execute the official release publication workflow (finalizing changelogs, renaming `RELEASE_vx.x.x.md`, updating release download links in README, or modifying `updated_mod_page.md`) unless the user EXPLICITLY states that an official release has been made or is being published (e.g., "publish release vX.X.X", "make a release").
